“比探探更好看”不能直接证明创新。当前产品假设是：**可解释的共同兴趣推荐，加上双向联系和清楚的退出控制，能让校园找搭子更自然、更有掌控感。** 这是待验证的设计假设。后续通过小规模访谈和任务测试检验，再决定哪些差异真正值得保留。

## 产品范围

核心使用场景：用户完善兴趣 → 浏览推荐及理由 → 喜欢／跳过 → 双向喜欢后聊天 → 随时解除、屏蔽或举报。

| 优先级 | 功能 | 本轮状态 | 完成标准 |
|---|---|---|---|
| Must | 注册、登录、资料、发现开关 | 已实现 | 输入校验，资料保存，未完善资料先补全 |
| Must | 推荐、筛选、共同兴趣说明 | 已实现 | 标签真实对应；无结果可恢复；隐藏与屏蔽资料排除 |
| Must | 喜欢、跳过、唯一双向匹配 | 已实现 | 单向不能聊天，重复喜欢不生成重复匹配 |
| Must | 匹配列表、文字聊天 | 已实现 | 双方保存与收取消息，第三人不能读写 |
| Must | 解除、屏蔽、举报、管理员查看 | 已实现基础版 | 失效联系不可继续聊天；举报需有处理记录 |
| Must | 手机与桌面可用 | 已做首轮检查 | 主要操作可见、表单可操作、无横向溢出；后续扩展设备验证 |
| Should | 用户研究与任务测试 | 待开展 | 保留同意、匿名记录、实际结果和改动对应 |
| Should | 数据导出／删除、保留期限、限流与账号恢复 | 待完成 | 有用户入口、权限测试、错误与恢复流程 |
| Should | 部署、安全与交接 | 待完成 | 新环境可复现，关闭演示开关，HTTPS，备份恢复验证 |
| Could | 可信且有授权的照片、活动或搭子邀约 | 暂缓 | 先证明用户需要，再确定权利与审核方案 |
| 暂不纳入 | 精确定位、手机号／通讯录抓取、付费、复杂机器学习 | 不开发 | 不挤占核心验证与报告工作 |

当前推荐采用兴趣集合重叠与相同交友意向的简单加权排序。UI 展示具体共同兴趣，不显示未经验证的“性格契合率”。应在用户研究后评价权重、冷启动与公平性，不将此描述为已验证的智能算法。

## 初始推进方案（历史记录）

下列为起步时的相对阶段方案；2026-11-02 起的当前执行计划以 [五周总计划](./team-plan/01_五周总计划.md) 为准：一周准备、两个两周 Sprint，按五人安排。本节保留最初计划，便于说明后续调整。初始方法采用一周一轮的迭代开发，结合 Kanban 看板。列为 Backlog → Ready → Doing → Review → Done；个人同时进行的主要任务限制为 1 项。每周计划、短进度同步、演示和回顾都留下简短记录。该方案是当前工作安排，团队成立后可以共同调整，并保留调整理由。

| 阶段 | 本阶段工作 | 可以验收的成果 | 应保留的证据 |
|---|---|---|---|
| 当前起步 | 解释课程要求、建立 Python 项目、完成基础流程 | 本地可运行版本、25 项后端测试、首轮界面检查 | 需求依据、代码与测试、已知缺口 |
| 第一轮 | 明确目标人群与核心问题，拟定访谈，核实课程日期；讨论方法和角色 | 需求基线、用户故事、核心流程、六人职责与 PDP | 真实研究记录、会议结论、最初计划 |
| 第二轮 | 根据反馈细化界面和推荐；补齐账号与隐私能力 | 经团队评审的完整核心流程和风险处理 | 设计备选、PR 与评审、权限测试、失败修复 |
| 第三轮 | 组织任务测试，修复主要问题，完成可复现部署方案 | 测试报告、改进版本、安装和恢复说明 | 原始任务结果、修复前后、方法调整 |
| 第四轮 | 冻结核心范围，准备演示与交接；每人整理反思证据 | 不超过 15 分钟的视频草稿与个人反思初稿 | 脚本、真实负责人、证据引用、反思覆盖检查 |
| 提交前 | 复核最终文档、链接、命名、备份和上传结果 | 每份反思完整、视频可访问、提交可确认 | 最终版本与实际上传确认 |

这些是相对阶段，不是教师规定的课表。核实截止日期后再安排日历、缓冲和负责人。若时间压缩，优先保留核心流程、用户测试、个人反思与视频，先移除扩展功能。

## 团队协作与真实贡献

当前暂按五人安排，开发主责及特色职责见 [角色草案](./team-plan/02_五人复合角色与协作规则.md)，待团队讨论确认。每个人都应有可解释的技术或设计成果、交叉评审和个人反思材料；不能只靠最后录视频或集中补提交。

当前使用 Trello 跟踪任务，用小范围 GitHub PR 连接真实修改与评审，由 A 在交叉复核后合并；Issue 可补充记录具体缺陷。成员使用自己的账号；不冒名提交、不拆空提交凑数量。初始代码属于 AI 辅助搭建，后续必须记录谁理解、修改、验证和维护了哪些部分，并按课程要求确认 AI 使用与引用规则。

Done 的条件：满足用户故事验收、相应检查通过、可在另一环境复现、影响行为的文档更新、证据链接已记下。截图和测试通过都不等于真实用户已经满意。

## 用户研究与评价计划

1. 团队确认后邀请少量自愿同学，了解找搭子时的现有办法、难点和顾虑；计划数量可从 4–6 人起步，根据可用时间调整。这些访谈目前尚未开展。
2. 使用虚构资料测试“完善兴趣、理解推荐理由、形成匹配、发送消息、停止联系”五类任务。记录是否独立完成、卡住的位置、时间和参与者原话；仅收必要的匿名资料。
3. 按问题严重程度排序，至少对影响主要任务的问题做一次有依据的改进；保留前后版本与相同任务的复测结果。
4. 产品评价同时覆盖可用性、访问权限、错误状态、性能与可持续维护。小样本结果只支持本次参与者与场景，不推广为全部大学生的结论。
5. 团队评价结合 Tuckman 阶段与真实事件，分析分歧如何处理、看板是否有效、是否出现等待或分工失衡，以及调整是否产生效果。

## 伦理法律与风险工作

主题 2 的伦理法律责任必须有研究依据。当前仅完成了减少收集、双向同意、隐藏资料与屏蔽等工程措施；尚未完成完整法律研究，也未形成合规结论。

| 风险 | 当前处理 | 下一步与触发条件 |
|---|---|---|
| 不希望被联系、骚扰 | 双向喜欢后聊天，解除与屏蔽，举报记录 | 测试边界与管理员处理流程，明确响应职责 |
| 隐私和过量收集 | 不要手机号、通讯录或精确定位；资料可隐藏 | 真实测试前明确告知、处理依据、导出删除和保留期限 |
| 未成年人参与 | 限 18 岁以上自我声明 | 核实目标人群和适用规则，说明声明不是核验 |
| 照片与设计版权 | 当前无人物照片；使用自建界面与文字头像 | 后续只用有明确权利的素材，记录来源和授权 |
| 账号滥用和部署暴露 | CSRF、密码哈希、参与者权限、开发身份开关 | 限流、恢复、生产配置审查与 HTTPS 验证 |
| 推荐偏差、过度外貌评价 | 用兴趣与意向，展示共同标签 | 研究不同使用者反馈，避免夸大匹配效果 |
| 环境与社会影响 | 简单单体架构、有限轮询、无上传媒体 | 评价资源成本与孤独／排斥等潜在效果 |
| 时间或协作失衡 | 小迭代、任务限量、评审与证据模板 | 每周回顾调整范围；具体负责人后续确定 |

确定实际测试和部署地区后，再用官方原文核实适用的数据保护、平台内容责任及版权规则，记录条款与具体设计的对应关系。实施一个功能不能代替法律论证。

## 视频与反思验收

建议视频长度约 14 分钟：问题和需求 1.5 分钟；研究与设计 2 分钟；真实核心演示 5 分钟；测试与产品／团队评价 2.5 分钟；接手开发、局限与下一步 2 分钟。说明各功能的真实负责人，展示实际工作版本，完整覆盖 assessment p5 的五个问题。制作质量不是单独评分项，应优先保证内容和证据清楚。

个人反思按原模板五部分准备：项目经历、团队、项目管理、伦理法律、职业发展。写作基本链条为“具体事件 → 本人的行动与理由 → 可查证结果 → 局限及不同解释 → 下一次改进”。实际感受与个人经历只能由本人提供；不提前写成已经发生的访谈、冲突、领导或贡献。

提交检查包括：全部问题回应、PDP 前后变化、来源引用、本人贡献证据、视频 URL、姓名与学号、规定文件名、Word/PDF 内容完整、截止时间、备份，以及上传后重新打开验证。
